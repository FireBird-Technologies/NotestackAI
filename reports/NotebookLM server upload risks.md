# Server Imports Turn Convenience Into Custody

**Sending NotebookLM chats and sources to a Notestack-owned server is not categorically forbidden by the official material reviewed, but it changes the product from a local exporter into a custodian of potentially sensitive, confidential, and copyrighted data.** That change is consequential: Chrome requires a prominently disclosed, narrowly defined purpose, affirmative informed consent, secure handling, and consistency between the extension UI, store listing, privacy policy, and actual network behavior. Google documents Takeout and item-level exports for personal NotebookLM, but no public consumer API for enumerating notebooks or retrieving full chats and source text; private RPC use or DOM scraping is therefore unsupported and brittle, with additional Terms risk if the implementation bypasses protections or disregards machine-readable access restrictions. Google’s stronger Workspace promises do not follow content into Notestack, and a user who can view a notebook may still lack authority to copy employer, client, licensed, or shared material into another service. The defensible design is a hybrid: preserve local download, make server import a distinct opt-in action, extract in the browser, send only the user-selected payload—not Google credentials—and store it under strict tenant isolation, retention, deletion, and staff-access controls. **Direct server import should not launch until those controls, disclosures, rights checks, and incident procedures are working end to end.**

## Chrome permits server import only within a narrow, disclosed purpose

Chrome treats scraped page content, website content, request and response data, personal communications, user-generated content, browsing activity, and authentication information as user data. Its policies require an accurate privacy policy, prominent disclosure of collection, use, sharing, and receiving parties, plus affirmative and informed user consent; since August 2026, Chrome has emphasized that all extension data collection must be prominently disclosed, even when it supports the extension’s main purpose. A privacy-policy link alone is not enough because the disclosure must appear in-product before the user agrees. **Changing a button labeled “Download” so it silently uploads to Notestack would therefore create a direct disclosure and consent problem.** The UI should present “Download locally” and “Import to Notestack” as separate actions and state the selected notebook, content categories, destination workspace, storage/processing behavior, and deletion terms immediately before import. ([Chrome Web Store Program Policies](https://developer.chrome.com/docs/webstore/program-policies/policies); [Chrome User Data FAQ](https://developer.chrome.com/docs/webstore/program-policies/user-data-faq); [2026 Chrome Web Store policy update](https://developer.chrome.com/blog/cws-policy-updates-2026))

Chrome’s Limited Use rules are more restrictive than a generic privacy notice: an extension may collect, use, and transmit only data necessary for its disclosed single purpose, including scraped, aggregated, de-identified, and derived data. Transfers are confined to providing or improving that purpose and narrow legal or security cases; advertising, data-broker resale, and creditworthiness uses are prohibited, while human access is generally barred except for specified exceptions such as the user’s consent to read particular data, security investigation, or legal compliance. Modern cryptography and secure authentication-data handling are explicit requirements. **Notestack should consequently exclude imported content from advertising, unrelated analytics, generalized model training, and routine support access; it must disclose every cloud, logging, AI, OCR, search, or support provider that actually receives the content.** ([Chrome Web Store Program Policies](https://developer.chrome.com/docs/webstore/program-policies/policies); [Chrome Web Store Developer Agreement](https://developer.chrome.com/docs/webstore/program-policies/terms))

The distinction between what is prohibited and what is merely risky matters. Hosting selected content on Notestack’s own backend is not itself prohibited when server storage is necessary for the disclosed product purpose. Undisclosed collection, unnecessary collection, prohibited secondary uses, insecure transmission, and certain transfers are policy violations. By contrast, DOM extraction from a page the user can already view is not expressly prohibited in the documentation reviewed, but it remains operationally fragile and fact-dependent under Google’s Terms. Google prohibits bypassing protective measures, prohibited reverse engineering, automated access that violates machine-readable instructions, and using Google AI-generated content to develop machine-learning models or related AI technology; it may suspend access for harmful scraping, including content that does not belong to the user. ([Google Terms of Service](https://policies.google.com/terms?hl=en); [Google Workspace Service-Specific Terms](https://workspace.google.com/terms/service-terms/))

## Google provides export paths, not a consumer integration contract

Google officially points personal users to Google Takeout and supports selected item-level exports, such as reports to Docs and tables to Sheets. Its documented notebook and source APIs belong to the separately licensed Gemini Notebook Enterprise product, use Google Cloud IAM, and are currently Preview/Pre-GA. **No official public consumer API was identified for listing personal notebooks, retrieving complete chat history, or bulk-downloading source text.** This absence does not prove that every user-initiated browser extraction is forbidden, but it means Notestack has no stable consumer API contract: selectors, virtualized chat markup, and private RPC formats can change without notice, exports can become incomplete, and replaying undocumented requests creates a materially stronger unauthorized-access and reverse-engineering concern than reading rendered content after a visible user action. ([Google Workspace Privacy Hub](https://support.google.com/a/answer/15706919?hl=en); [Google Takeout help](https://support.google.com/accounts/answer/3024190?hl=en); [Gemini Notebook Enterprise API](https://docs.cloud.google.com/gemini/enterprise/notebooklm-enterprise/docs/api-notebooks))

The lower-risk hierarchy is therefore clear. Google Takeout import is the strongest official bulk route for consumer accounts, though asynchronous and potentially awkward. The Enterprise API is the supported programmatic route for eligible organizational customers, subject to licensing and Preview conditions. A packaged Chrome extension may use user-visible DOM extraction as a convenience fallback, but should avoid Google cookies, authorization headers, CSRF values, session tokens, hidden endpoints, restriction bypasses, and backend-controlled automation logic. Manifest V3 requires functional logic to remain packaged and reviewable; a server may return data and job status, but it must not remotely supply executable selector logic, JavaScript, WebAssembly, or an instruction language that changes extraction behavior outside review. ([Manifest V3 requirements](https://developer.chrome.com/docs/webstore/program-policies/mv3-requirements); [Chrome remote-hosted-code guidance](https://developer.chrome.com/docs/extensions/develop/migrate/remote-hosted-code); [Google API Services User Data Policy](https://developers.google.com/terms/api-services-user-data-policy))

## A backend creates privacy, security, and organizational exposure

Local export leaves Notestack with little or no custody of the notebook body. Server import creates another copy in Notestack’s databases, object storage, queues, search indexes, vector stores, previews, backups, logs, and vendors. Notebook material can include health or financial records, credentials, legal work, unpublished research, customer information, personal communications, and data about people who never interacted with Notestack. **The aggregate backend becomes a high-value, multi-tenant breach target, and a single authorization or isolation failure can expose many users rather than one local file.** International privacy principles and regulatory guidance converge on purpose limitation, minimization, security, limited retention, transparency, individual access and deletion, processor oversight, and accountability; the exact lawful basis and organizational role vary by jurisdiction and cannot be solved by calling every click “consent.” ([OECD Privacy Guidelines](https://legalinstruments.oecd.org/public/doc/114/body-text.en.html); [ICO data-protection principles](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/data-protection-principles/a-guide-to-the-data-protection-principles/); [FTC business data-security guide](https://www.ftc.gov/business-guidance/resources/protecting-personal-information-guide-business))

Google’s own safeguards also stop at the transfer boundary. Qualifying Workspace and Education accounts receive commitments that uploads, queries, and model outputs are not human-reviewed or used to train AI models, while the consumer product has different feedback-dependent rules. Google further notes that NotebookLM copies of Drive sources do not inherit all Drive controls and that organizational feature protection depends on license. Once the extension sends the material to Notestack, Google’s Workspace agreement, Cloud Data Processing Addendum, retention behavior, access controls, and no-training/no-human-review promises do not govern the new copy. A work or school user’s ability to view content is not proof that their organization permits export to a new SaaS vendor, region, or subprocessor. ([NotebookLM privacy and terms](https://support.google.com/gemininotebook/answer/17004255?hl=en); [NotebookLM for work or school](https://support.google.com/gemininotebook/answer/16337734?hl=en); [Google Workspace Privacy Hub](https://support.google.com/a/answer/15706919?hl=en))

The server must consequently behave like a sensitive document system, not a simple upload endpoint. It should use short-lived Notestack credentials scoped to a destination workspace; authorize every upload, finalize, read, and delete request on the server; namespace every object and derived artifact by tenant; encrypt transport and storage with managed keys; keep document bodies and secrets out of telemetry; deny staff content access by default; and make deletion propagate through primary storage, search/vector indexes, queues, temporary files, replicas, and scheduled backup expiry. Uploaded files must be treated as hostile: enforce count and size limits, validate file signatures, normalize names, control decompression, quarantine and scan files, isolate parsers, and never execute embedded macros or scripts. These controls reflect NIST guidance on access, encryption, risk, and incident response, plus OWASP guidance for authorization, cryptographic storage, logging, and safe uploads. ([NIST SP 800-122](https://csrc.nist.gov/pubs/sp/800/122/final); [NIST SP 800-61 Rev. 3](https://csrc.nist.gov/pubs/sp/800/61/r3/final); [OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html); [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html))

## Copying every source can erase rights boundaries

Notebook access and redistribution rights are different. Google tells users to avoid uploading material they do not have rights to, to respect copyright and privacy, and not to share copyrighted material without the necessary rights. Shared notebooks distinguish owners, editors, and viewers; some Play Books sources and publisher-controlled artifacts have additional restrictions. A bulk “all notebooks” transfer can flatten those boundaries by copying employer files, client documents, shared Drive content, licensed books, and sources that later become inaccessible after the user loses Drive permission. **Possession of rendered text is not evidence of ownership or authority to reproduce it on another platform.** ([Add or discover NotebookLM sources](https://support.google.com/gemininotebook/answer/16215270?co=GENIE.Platform%3DDesktop&hl=en); [Create a notebook](https://support.google.com/gemininotebook/answer/16206563?hl=en); [NotebookLM privacy and terms](https://support.google.com/gemininotebook/answer/17004255?hl=en))

This is not theoretical copyright housekeeping: transmitting a protected work generally creates another digital copy, and the copyright owner’s exclusive rights include reproduction and distribution. Fair use is case-specific; education or research does not automatically make full-source copying lawful. Notestack should preserve provenance and copyright notices, default imports to private, let users exclude individual sources, require a rights confirmation, grant itself only the narrow license needed to host/process content at the user’s direction, and maintain a complaint/takedown process. Generated chat answers should be handled as potentially containing quoted protected expression, not assumed to be purely user-owned text. ([U.S. Copyright Office overview](https://www.copyright.gov/what-is-copyright/); [U.S. Copyright Office fair-use FAQ](https://www.copyright.gov/help/faq/faq-fairuse.html); [17 U.S.C. §107](https://www.copyright.gov/title17/92chap1.html))

## A phased architecture turns risks into launch gates

The recommended flow keeps discovery and extraction local, then makes the destination change unmistakable. The user chooses local download or a separate Notestack import, selects chat, sources, or both, sees item count and size plus the destination workspace and processing/retention summary, and confirms. The extension obtains a short-lived Notestack upload session and sends only the selected content over TLS—never Google passwords, cookies, tokens, browser storage, or raw authentication headers. The server reauthorizes each operation, quarantines files, stores them in encrypted tenant-scoped locations, records content-free audit events, runs derived processing in isolated least-privilege workers, reports per-item progress, supports cancellation and resumable retries, and exposes complete export/deletion controls. **Local download should remain available as the privacy-preserving path and as the fallback when the user or organization cannot approve server custody.**

| Launch gate | Go-live requirement |
|---|---|
| Disclosure and user direction | Store listing, dashboard declarations, privacy policy, network behavior, and in-product just-in-time disclosure agree; import is separate from download and requires an affirmative action scoped to selected notebooks/content. |
| Google access boundary | No Google credentials or reusable session material leave the browser; no protection or publisher restriction is bypassed; supported Takeout/Enterprise API paths are preferred; any DOM fallback is user-initiated and isolated behind maintainable failure handling. |
| Authorization and isolation | The server verifies Notestack identity, workspace membership, and object permission on every request; horizontal/vertical access tests and tenant-isolation tests pass. |
| Data lifecycle | A documented inventory, purpose, retention matrix, subprocessor register, processing-location map, user export, and deletion workflow cover originals, derived artifacts, logs, queues, and backup expiry. |
| Security operations | TLS, encryption at rest, managed keys, hostile-file controls, content-free logging, monitoring, incident response, breach notification, recovery testing, and restricted audited staff access are implemented and tested. |
| Rights and enterprise readiness | Imports are private by default; source exclusion, provenance, rights confirmation, and takedown handling exist; work/school deployments have an organizational approval path and appropriate contractual/privacy review. |
| Secondary use | Imported content is excluded from ads, sale, unrelated analytics, model training, evaluation, and generalized product improvement unless a separately reviewed purpose and valid user/organizational controls are established. |

The safest release sequence is local-only Markdown/ZIP first, opt-in chat/Markdown import second after identity, isolation, encryption, retention, deletion, and incident controls pass, source-file import third after the hostile-file and copyright pipeline is ready, and indexing or AI processing last after separate vendor, purpose, and model-use review. A go/no-go decision also requires review of the actual data-flow diagram, hosting regions, vendors, privacy notice, product terms, threat model, and penetration-test results; public policy pages cannot validate the implementation.

## Conclusion

The key product boundary is not “our server versus a third-party server.” It is **local user-controlled copying versus centralized platform custody**. A Notestack-owned backend may reduce one class of external transfer, yet its cloud hosts, monitoring tools, model providers, staff workflows, and backups still widen the circle of access and make Notestack accountable for content it previously never possessed.

Server import can be a legitimate and valuable feature when it is an explicit destination chosen by the user, not an invisible transport hidden behind export. Treating privacy, rights, tenant isolation, deletion, and unsupported Google access as launch architecture—not post-launch paperwork—turns the feature from a data-exfiltration risk into a defensible import workflow.
