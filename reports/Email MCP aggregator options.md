# Choose the right email MCP layer

**For a single provider that connects your users' existing Gmail, Microsoft 365, Exchange, Yahoo, iCloud, and IMAP mailboxes, start with Nylas.** It offers hosted US and EU MCP endpoints, a normalized email API, delegated mailbox grants, narrowly scoped agent credentials, and a two-step confirmation flow before sending ([Nylas MCP](https://developer.nylas.com/docs/dev-guide/mcp/); [Email API](https://developer.nylas.com/docs/v3/email/)). If NotestackAI needs email plus many unrelated apps such as Canva, Slack, or CRMs, test **Composio** first and **Pipedream Connect** second: both provide hosted MCP infrastructure, managed authentication, and application-level user mapping ([Composio sessions](https://docs.composio.dev/docs/sessions-via-mcp); [Pipedream for developers](https://mcp.pipedream.com/developers)). If the goal is only to send product or transactional email from domains your company controls, use **Resend** instead of a mailbox aggregator; its official remote MCP can send and receive mail and manage contacts, broadcasts, and domains ([Resend MCP](https://github.com/resend/resend-mcp/blob/main/README.md)). These are three different problems, so one product should not be selected until the product flow is clear.

## “Many providers” and “many domains” require different architectures

An email **provider** hosts a mailbox: Gmail/Google Workspace, Outlook/Microsoft 365, Fastmail, Zoho, or an IMAP server. A **custom domain** is the address after `@`, and it can be hosted by any of those providers. A company address such as `person@company.com` may therefore connect through Gmail or Microsoft OAuth without needing generic SMTP. Nylas, Aurinko, EmailEngine, and similar unified-mail products act through each user's existing provider; they are the right category when the application must read, search, reply, draft, or send as the user ([Nylas Email API](https://developer.nylas.com/docs/v3/email/); [Aurinko Email API](https://docs.aurinko.io/unified-apis/email-api); [EmailEngine](https://emailengine.app/)).

A transactional sender such as Resend, Mailgun, Postmark, or Amazon SES works differently: the application verifies domains it controls, then sends through the vendor's delivery network. It does not connect arbitrary customer inboxes. A broad MCP aggregator such as Composio or Pipedream is a third category: it exposes provider-specific Gmail and Outlook tools alongside hundreds or thousands of non-email integrations, but it does not normalize every mailbox behind one universal email schema ([Composio Gmail](https://docs.composio.dev/toolkits/gmail); [Composio Outlook](https://docs.composio.dev/toolkits/outlook); [Pipedream app catalog](https://pipedream.com/apps)).

## NotestackAI should validate two paths, not one compromise

For the existing outbound-MCP connection feature, the most direct proof of concept is **Nylas for customer-owned mailboxes**. Store the Nylas grant/account identifier against the local user or workspace, issue only a resource-scoped credential, and expose a small tool set: search, read, create draft, send confirmed draft, reply, and attach. This produces consistent tool contracts across Gmail, Microsoft 365, and IMAP while retaining provider-specific authentication behind one service. Nylas currently lists five connected email/calendar accounts free, then paid connected-account tiers, so production cost should be modeled per active mailbox rather than per message ([Nylas pricing](https://www.nylas.com/pricing/)).

In parallel, test **Composio** if the real product direction is a general “connect external apps” layer. Its application sessions map naturally to a local `user_id`, and one session endpoint can be restricted to selected toolkits ([Composio sessions](https://docs.composio.dev/docs/sessions-via-mcp)). This avoids designing the product around email-specific schemas when Canva and other SaaS integrations are equally important. Keep **Resend** as a separate system connection for NotestackAI-owned notifications, sharing, onboarding, and campaign mail; do not route those through a user's mailbox.

The acceptance test should use both a custom-domain Google Workspace account and a Microsoft 365 tenant. Verify connect, revoke/reconnect, search, read, draft, confirmed send, reply-in-thread, attachment handling, tenant-admin consent, and strict cross-user isolation. If arbitrary IMAP/SMTP accounts are commercially important, add one non-Google/Microsoft host to the test; broad aggregator catalogs do not by themselves prove complete generic-mail support.

## OAuth and agent safety dominate production risk

Delegated OAuth is the hard part, not MCP transport. Gmail send/read scopes can trigger Google verification, and Microsoft tenants can require administrator consent. Production deployments should use the application's own Google and Microsoft OAuth clients for branding, quota ownership, and scope control where the selected vendor supports them. Generic IMAP/SMTP expands provider coverage but can introduce password or app-password handling and loses richer provider concepts such as Gmail labels, native threads, and Microsoft tenant policy.

Every credential and tool call must be tenant-scoped. Use draft-first behavior or explicit approval for sending, recipient and rate limits for automated actions, immutable audit records, and prompt revocation. Nylas already requires a two-step confirmation hash for its MCP send tools and recommends narrowly scoped IAM keys ([Nylas MCP security](https://developer.nylas.com/docs/dev-guide/mcp/)). Package provenance also matters: Postmark disclosed a malicious namesake npm package that secretly BCC'd messages, so pin dependencies and use only vendor-linked repositories ([Postmark warning](https://postmarkapp.com/blog/postmark-labs-teaching-ai-to-speak-email-with-our-new-mcp-server)).

## Conclusion

The cleanest product boundary is **Nylas for users' mailboxes, Resend for application-owned sending, and Composio only if NotestackAI is deliberately becoming a broad integration platform**. This is more reliable than forcing mailbox access, transactional delivery, and unrelated SaaS tools through one abstraction.

A provider-neutral interface is valuable, but only at the tool-contract level. Authentication, consent, threading, shared mailboxes, aliases, and rate limits remain provider-specific, so the final vendor choice should follow a short tenant-isolation and feature-parity proof of concept rather than catalog size alone.
